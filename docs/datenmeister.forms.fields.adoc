= Form Fields Architecture and Reference (Server & Client)
:toc:
:toclevels: 3
[#dm_form_fields]

== Overview

In DatenMeister, **Form Fields** represent the atomic UI and data-binding building blocks used within forms (such as `RowForm`, `TableForm`, and `ObjectForm`). Form fields bridge the semantic MOF/UML metamodel stored on the server with interactive, type-safe user interface controls rendered on the client (Web UI via TypeScript/HTML/jQuery and Desktop UI via WPF).

The form field architecture consists of two cooperative layers:

1. **Server-Side Generation & Metamodel**: The server analyzes metaclasses or runtime object properties, instantiating MOF form field definitions (`FieldData` specializations) via `IFieldFactory` implementations and `FormCreationContext`.
2. **Client-Side Rendering & Evaluation**: The client receives field definitions and executes field controllers implementing `IFormField` (extending `BaseField` in TypeScript). The client is responsible for rendering DOM elements (`createDom`) in read-only or edit modes, handling user events, and serializing modified values back to the model (`evaluateDom`).

[#dm_form_fields_architecture]
== Architecture & Lifecycle

=== 1. Server-Side Field Pipeline (`IFieldFactory`)

On the server, fields are created during the execution of form creation passes (e.g., when generating `RowForm` or `TableForm`). The server-side pipeline is driven by `IFieldFactory`:

[source,csharp]
----
public interface IFieldFactory : IFormFactoryBase
{
    void CreateField(
        FieldFactoryParameter parameter,
        FormCreationContext context,
        FormCreationResultOneForm result);
}
----

The `FieldFactoryParameter` encapsulates all metadata required to determine the field type:

* `Property`: The MOF/UML property definition (`IElement`) containing type classifiers, multiplicity (`isMultiple`), and containment semantics (`isComposite`).
* `PropertyName`: The identifier of the property being mapped.
* `PropertyValue`: The runtime value of the property (when generating forms data-first).
* `IsInTable`: Boolean flag indicating whether the field is placed within a table cell (suppressing deep nested forms to prevent recursion).
* `MetaClass`: The containing classifier.

==== Standard Server-Side Field Factories

[cols="2,2,4",options="header"]
|===
|Factory Class |Priority / Order |Behavior & Creation Logic

|`FieldFromPropertyType`
|Priority: 1000 (Metaclass-driven)
|Inspects property types via `TypeIndexLogic`:
* UML `Enumeration` -> `DropDownFieldData` (populated with `ValuePair` entries)
* `PrimitiveTypes.Boolean` -> `CheckboxFieldData`
* `PrimitiveTypes.DateTime` -> `DateTimeFieldData`
* Primitive types (`String`, `Integer`, `Real`, `UnlimitedNatural`) -> `TextFieldData` (integer fields default to narrower widths)
* Collection properties (`isMultiple = true`) -> `SubElementFieldData`
* Non-composite references -> `ReferenceFieldData` (or `DropDownByQueryData` if configured)
* Composite properties (`isComposite = true`) -> `CompositeFieldData`

|`FieldFromPropertyValue`
|Priority: 500 (Data-driven fallback)
|Inspects runtime .NET object types when no metamodel property exists:
* `DotNetHelper.IsEnumeration(type)` -> `SubElementFieldData`
* `IObject` reference -> `ReferenceFieldData`
* Primitive / string values -> `TextFieldData`

|`FieldAnyFieldData`
|Priority: 0 (Generic fallback)
|Provides catch-all field generation producing `SubElementFieldData` (if collection) or `AnyDataFieldData`.
|===

=== 2. Client-Side Field Architecture (`IFormField` & `BaseField`)

In the Web UI (`DatenMeister.WebServer`), all fields implement `IFormField` and typically inherit from the abstract base class `BaseField` (defined in `Interfaces.ts`):

[source,typescript]
----
export interface IFormField {
    readonly context: IFieldRenderContext;
    readonly configuration?: IFormConfiguration;
    readonly field: Mof.DmObject;
    readonly isReadOnly: boolean;
    readonly itemUrl: string;
    readonly form: IFormNavigation;

    createDom(dmElement: Mof.DmObject): Promise<JQuery<HTMLElement>>;
    evaluateDom(dmElement: Mof.DmObject): Promise<void>;
    showNameField?(): boolean;
    showValue?(): boolean;
    callbackUpdateField?: () => void;
    destroy?(): void;
}
----

==== Execution Lifecycle

1. **Registration & Creation (`FieldFactory.ts`)**:
   Field types register their factory delegates via `registerField(metaClassUri, factoryMethod)`. When rendering a form, `FieldFactory.createField(context)` queries the registry by the field's `metaClass.uri` and returns the matching `IFormField` instance (falling back to `UnknownField` if unregistered).
2. **DOM Generation (`createDom`)**:
   Constructs the jQuery HTML representation for the field.
   * **Read-Only Mode (`isReadOnly === true`)**: Renders static text, hyperlinks, inline reference labels via `injectNameByUri`, badges, or compact lists.
   * **Edit Mode (`isReadOnly === false`)**: Renders interactive inputs (`<input>`, `<textarea>`, `<select>`, modal pickers, action buttons).
3. **Data Binding & Sync (`evaluateDom`)**:
   Extracts user input from the DOM and writes it back into `dmElement` using `dmElement.set(propertyName, value)` or `dmElement.unset(propertyName)`.
4. **Layout Hints**:
   * `showNameField()`: If `false`, suppresses the label column in a `RowForm`, allowing the field value to span the full width.
   * `showValue()`: If `false`, hides the checkbox indicating whether a property is set (used by action buttons and visual separators).
5. **Change Notification (`callbackUpdateField`)**:
   Invoked on input/change events to notify parent forms to update validation, enable save buttons, or trigger dependent field recalculations.

=== 3. Desktop Client Counterpart (WPF)

In the WPF desktop client (`DatenMeister.WPF`), fields implement `IDetailField` via `DatenMeister.WPF.Forms.Fields.FieldFactory.CreateField(value, field)`:

* `CreateElement(value, fieldData, detailForm, fieldFlags)`: Generates WPF `UIElement` controls (e.g. `TextBox`, `CheckBox`, `ComboBox`, custom controls).
* `CallSetAction(element)`: Applies edited values back to the target MOF element.

== Form Field Types Reference

=== Base Type: FieldData

`FieldData` is the abstract base definition for all field elements in DatenMeister. All specialized fields inherit these core properties.

[cols="2,1,1,4",options="header"]
|===
|Property |Type |Default |Description

|`name`
|String
|`""`
|Name of the field matching the underlying property name of the MOF element.

|`title`
|String
|`""`
|Human-readable title/label displayed in form headers and row labels.

|`isReadOnly`
|Boolean
|`false`
|When set to `true`, forces the field into read-only display mode regardless of form-level permissions.

|`defaultValue`
|Any
|`null`
|Default value populated when creating new items if no value is explicitly supplied.

|`isEnumeration`
|Boolean
|`false`
|Flag indicating whether the property represents a collection/array of values rather than a scalar value.

|`isAttached`
|Boolean
|`false`
|Flag indicating whether the property is attached dynamically as an extent annotation rather than stored directly in the object.
|===

=== TextFieldData

Represents a text input control for single-line or multi-line strings.

* **Metaclass URI**: `dm:///_internal/types/internal#DatenMeister.Models.Forms.TextFieldData`
* **TypeScript Implementation**: `TextField.ts`
* **WPF Implementation**: `TextboxField.cs`

==== Properties

[cols="2,1,1,4",options="header"]
|===
|Property |Type |Default |Description

|`lineHeight`
|Number
|`1`
|Number of visible lines. If `1` or unspecified, renders a single-line `<input class='dm-textfield' />`. If `> 1`, renders a multi-line `<textarea class='dm-textfield' />`.

|`width`
|Number
|`70` (input) / `80` (textarea)
|Width of the input control in character columns (`size` attribute for inputs, `cols` attribute for textareas).

|`shortenTextLength`
|Number
|`0` (disabled)
|If greater than `0`, truncates displayed text to this length in read-only mode using word-boundary truncation. (In table views, `TableForm` automatically truncates long text).

|`supportClipboardCopy`
|Boolean
|`false`
|When `true`, renders a "Copy to Clipboard" button in read-only mode, with automatic fallback for non-secure browser contexts.
|===

==== Client-Side Behavior
* **Read-only**: Formats empty/null values as `<em class='dm-undefined'>undefined</em>`. If the property name is `name`, automatically enriches the text with item links using `injectNameByUri`. If an array of strings is passed, renders an unstyled list (`<ul>`).
* **Edit**: Captures `input` and `change` events, writing string values back via `evaluateDom`.

* **Metaclass URI**: `dm:///_internal/types/internal#DatenMeister.Models.Forms.DateTimeFieldData`

[cols="2,1,1,4",options="header"]

|Boolean
|`false`

|`hideTime`
|Boolean
|`false`

==== Client-Side Behavior
* **Read-only**: Formats parsed ISO date strings as `YYYY-MM-DD HH:mm`.

* **Evaluation**: `evaluateDom` parses date and time inputs into a JavaScript `Date` object and serializes it as an ISO 8601 UTC string (`toISOString()`).

[#dm_form_fields_extending]
== Implementing Custom Form Fields

To add a new custom field type to DatenMeister:

1. **Define the Metamodel in MOF / C#**:
   Create a new class under `_DatenMeister._Forms._FieldTypes` inheriting from `FieldData` and assign a unique Type URI.
2. **Server-Side Generation**:
   Implement `IFieldFactory` in C# to automatically construct the field definition during form building, and register it in `FormCreationContext.FieldFormFactories`.
3. **Client-Side Rendering (TypeScript)**:
   Create a new class extending `BaseField` in `Assets/js/datenmeister/fields/` implementing `createDom()` and `evaluateDom()`.
4. **Register in Field Factory**:
   Register the new TypeScript field in `FieldFactory.ts`:
   [source,typescript]
   ----
   import * as MyCustomField from "../fields/MyCustomField.js";

   registerField("dm:///_internal/types/internal#MyCustomFieldData", ctx => new MyCustomField.Field(ctx));
   ----
